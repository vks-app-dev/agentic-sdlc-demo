# REQ-001: Record and list expenses

Status: draft · Stage: requirements

## Problem
A single user has no way to keep track of what they spend through this API. Today it exposes only `/health`. Without a record of expenses (amount, currency, category, date, optional note) the user cannot see where money goes or how much was spent in a period or category. This is the first functional feature of the Expense API and the base for later reporting.

## User story
As an individual user, I want to record expenses and list them filtered by date range and category with a total, so that I can see how much I spent on what and when.

## Scope
**In scope**
- Create an expense with amount, currency, category, date and optional note.
- List expenses, optionally filtered by date range (from/to, inclusive) and by category.
- Return a total for the expenses matched by the list request, with the list.
- Input validation and clear error responses for invalid input.
- Persistence for the life of the process at minimum (in-memory or SQLite; choice is for Design).

**Out of scope**
- Authentication, authorization, multiple users or tenants.
- Editing or deleting expenses.
- Fetching a single expense by ID.
- Currency conversion or exchange rates.
- Pagination, sorting options, free-text search.
- Category management (a fixed or predefined category list, category CRUD).
- Reports, charts, export/import, recurring expenses, attachments.

## Acceptance criteria
- **AC-1** Create expense (main path)
  - Given an empty store
  - When a client submits a create request with amount `12.50`, currency `USD`, category `food`, date `2026-10-01` and note `lunch`
  - Then the response is 201 and returns the stored expense with a server-generated unique ID and the submitted values, and the expense appears in a subsequent list.
- **AC-2** Create expense without note
  - Given an empty store
  - When a client submits a create request with all required fields and no note
  - Then the response is 201 and the expense is stored with the note absent or null.
- **AC-3** Required fields
  - Given any store state
  - When a create request omits amount, currency, category or date (each tested separately)
  - Then the response is 422, naming the missing field, and nothing is stored.
- **AC-4** Amount validation
  - Given any store state
  - When a create request has an amount that is zero, negative, non-numeric, or has more than 2 decimal places
  - Then the response is 422 and nothing is stored.
- **AC-5** Amount precision
  - Given an expense created with amount `0.10` and another with `0.20`
  - When the expenses are listed
  - Then each amount is returned exactly as submitted and the total is exactly `0.30` (no floating-point error).
- **AC-6** Currency validation
  - Given any store state
  - When a create request has a currency that is not a 3-letter uppercase ISO 4217-style code (for example `usd`, `US`, `DOLLARS`, empty)
  - Then the response is 422 and nothing is stored.
- **AC-7** Date validation
  - Given any store state
  - When a create request has a date that is not a valid calendar date in `YYYY-MM-DD` format (for example `2026-02-30`, `10/01/2026`)
  - Then the response is 422 and nothing is stored.
- **AC-8** Category and note validation
  - Given any store state
  - When a create request has an empty or whitespace-only category, a category longer than 50 characters, or a note longer than 500 characters
  - Then the response is 422 and nothing is stored.
- **AC-9** List all with total
  - Given three stored expenses in USD with amounts `10.00`, `5.50` and `4.50`
  - When a client lists expenses with no filters
  - Then the response is 200, contains all three expenses, and the total is `20.00`.
- **AC-10** Empty list
  - Given an empty store
  - When a client lists expenses
  - Then the response is 200 with an empty list and a total of `0`.
- **AC-11** Filter by date range
  - Given expenses dated `2026-09-30`, `2026-10-01`, `2026-10-15` and `2026-10-31`
  - When a client lists with `from=2026-10-01` and `to=2026-10-15`
  - Then only the expenses dated `2026-10-01` and `2026-10-15` are returned (both bounds inclusive) and the total covers only those.
- **AC-12** Open-ended date range
  - Given the same four expenses as AC-11
  - When a client lists with only `from=2026-10-15`, and separately with only `to=2026-10-01`
  - Then the first request returns the expenses dated `2026-10-15` and `2026-10-31`, and the second returns those dated `2026-09-30` and `2026-10-01`.
- **AC-13** Filter by category
  - Given expenses in categories `food`, `travel` and `food`
  - When a client lists with `category=food`
  - Then only the two `food` expenses are returned and the total covers only those.
- **AC-14** Combined filters
  - Given expenses across several dates and categories
  - When a client lists with `from`, `to` and `category` together
  - Then only expenses matching all three conditions are returned and the total covers only those.
- **AC-15** No matches
  - Given stored expenses that do not match the supplied filters
  - When a client lists with those filters
  - Then the response is 200 with an empty list and a total of `0`.
- **AC-16** Invalid filter input
  - Given any store state
  - When a client lists with an invalid `from` or `to` date, or with `from` later than `to`
  - Then the response is 422 and no list is returned.
- **AC-17** Category matching is case-insensitive
  - Given an expense stored with category `Food`
  - When a client lists with `category=food`
  - Then that expense is returned. (Subject to Open question 2.)
- **AC-18** Multiple currencies
  - Given stored expenses of `10.00 USD` and `20.00 EUR`
  - When a client lists with no filters
  - Then both expenses are returned, and the total is reported separately per currency (`USD: 10.00`, `EUR: 20.00`), never summed across currencies. (Subject to Open question 1.)
- **AC-19** Duplicates allowed
  - Given an expense already stored
  - When a client submits a second create request with identical field values
  - Then the response is 201, a different ID is assigned, and the list shows both expenses and counts both in the total.
- **AC-20** Existing behaviour preserved
  - Given the application is running
  - When a client calls `GET /health`
  - Then the response is still `{"status": "ok"}`.

## Non-functional requirements
- Performance: List request returns within 200 ms for up to 10,000 stored expenses on a developer machine.
- Security / privacy: No authentication (explicitly deferred). Notes are free text and must not be logged. Input is validated and bounded in length. If SQLite is used, queries must be parameterised. Expense data is personal financial data, so the Design stage should decide whether a security review is needed (config triggers on `auth`, `pii`).
- Compatibility: Python 3.12, FastAPI, JSON over HTTP. Existing `/health` endpoint unchanged. Monetary amounts must not use binary floating point internally or in responses. Tests run with `uv run pytest` and must pass `uv run ruff check .`.

## Impact and estimate
- Areas of the codebase touched: `app/main.py` (register routes, or include a router); new modules under `app/` for expense models, storage and routes (structure to be set by Design); new tests under `tests/` (existing `tests/test_health.py` untouched); `pyproject.toml` only if a dependency is added.
- Size: M
- Risk: low, because it is greenfield code in a small codebase with no auth or external integrations. The main risks are money handling (precision, multi-currency totals) and unsettled business rules, listed below.

- [x] **Q1:** Multi-currency totals: should the total be reported per currency (assumed in AC-18), or should the list be restricted to a single currency, or should mixed currencies be rejected? There is no conversion in scope.
  **Answer:** yes per currency
- [x] **Q2:** Category: free text or a fixed list? Is matching case-insensitive and trimmed (assumed in AC-17)?
  **Answer:** free text
- [x] **Q3:** Should future-dated expenses be accepted? Is there a minimum date?
  **Answer:** yes
- [x] **Q4:** Is persistence across restarts required (SQLite), or is in-memory acceptable for now?
  **Answer:** SQLite
- [x] **Q5:** Maximum amount and allowed currency set: any upper bound? Any ISO 4217 code, or only a whitelist? Are currencies with 0 or 3 decimal places (JPY, KWD) needed (AC-4 assumes at most 2 decimals)?
  **Answer:** no limit
- [x] **Q6:** Should list results have a defined order (assumed: date descending, then creation order) given pagination is out of scope?
  **Answer:** date descending
- [x] **Q7:** Should the `from` and `to` parameters be named so, and is the API path to be `/expenses`? (Left to Design unless a client contract already exists.)
  **Answer:** yes
- [x] **Q8 (AC-9, AC-10, AC-18, blocking):** The shape of `total` is contradictory. AC-9 and AC-10 imply a single scalar (`20.00`, `0`), while AC-18 implies a per-currency map (`USD: 10.00, EUR: 20.00`). A client cannot code against both. Options: (a) always return a map keyed by currency, with an empty list giving `{}`; (b) return a scalar when one currency is present and a map otherwise (not recommended, because the type varies); (c) always return a list of `{currency, total}` objects. AC-9, AC-10 and AC-15 would need to be restated to match, including the empty-result total (`0` vs `{}`).
  **Answer:** option a
- [x] **Q9 (AC-4, AC-5, blocking):** What is the JSON wire representation of `amount` in requests and responses? JSON numbers are parsed as binary floats by many clients and by default by FastAPI, which conflicts with "no floating-point error" and "returned exactly as submitted". Options: (a) string only (`"12.50"`); (b) accept number or string, always return a string; (c) accept number via Decimal parsing. Also decide whether `12.5` is returned as `12.50` or `12.5` ("exactly as submitted" vs a fixed 2dp format), and whether `"12.500"`, `1e1`, `NaN`, `Infinity`, `" 12.50 "` and numeric strings count as "non-numeric" or "more than 2 decimal places".
  **Answer:** Options: (a)
- [x] **Q10 (AC-3, AC-4 to AC-8, AC-16, blocking):** The error response contract is not specified. Is the FastAPI default 422 body (`detail` list with `loc` and `msg`) acceptable as "clear" and "naming the missing field"? AC-16's custom `from` > `to` check will not produce that format automatically. Must all 422s use one consistent shape? Also, FastAPI echoes the submitted input (including `note`) in the 422 `input` field, which conflicts with the "notes must not be logged" NFR if validation errors are logged. Should the input be stripped from error bodies and logs?
  **Answer:** One error shape for every 4xx, including the `from` > `to` check: `{"error": {"code": "validation_error", "message": "...", "fields": [{"field": "amount", "message": "..."}]}}`. Validation errors return 422. Never echo submitted input (including `note`) in error bodies or logs. _(demo answer by Claude)_
- [x] **Q11 (AC-6, AC-8, AC-17, blocking):** Normalisation vs rejection is unspecified. AC-6 rejects lowercase `usd`, but AC-17 case-folds category. Is category stored and returned as submitted (`Food`) or normalised? Is leading and trailing whitespace trimmed before the 1-50 length check (is `" food "` valid, and does it match `category=food`)? Is the length counted in characters or bytes? Is an empty `note` (`""`) accepted and stored as `""` or `null`? AC-1 says the response returns "the submitted values", which is contradicted if any normalisation happens.
  **Answer:** Category: trim whitespace, then require 1-50 characters; stored and returned as trimmed, case kept (`Food`); filtering is case-insensitive. Currency: no normalisation, lowercase is rejected (AC-6 stands). Note: trimmed; empty note is stored and returned as `null`. "Submitted values" in AC-1 means after trimming. _(demo answer by Claude)_
- [x] **Q12 (AC-1, AC-19, blocking):** What is the ID format (integer sequence, UUID)? Does "unique" need to hold across restarts if persistence (Q4) is chosen? Also confirm the exact create response fields (`id`, `amount`, `currency`, `category`, `date`, `note`) and whether a `created_at` timestamp is included. A timestamp would make AC-19 and the ordering in Q6 depend on the clock.
  **Answer:** UUID v4 string, unique across restarts. Create response fields: `id`, `amount`, `currency`, `category`, `date`, `note`, `created_at` (UTC, ISO 8601). List order: `date` descending, then `created_at` descending as a tie-break. _(demo answer by Claude)_
- [x] **Q13 (AC-7, non-blocking):** Is a full ISO datetime (`2026-10-01T10:00:00Z`) or a date with a time zone rejected? AC-7 says strict `YYYY-MM-DD`, but Pydantic's date parsing also accepts other forms (for example integer timestamps and datetime strings with a zero time) unless run in strict mode. Confirm that strict `YYYY-MM-DD` is intended and that the date is a plain calendar date with no time zone conversion (no "today" boundary issues).
  **Answer:** Strict `YYYY-MM-DD` only. Reject datetimes, time zones and timestamps. It is a plain calendar date with no time zone conversion. _(demo answer by Claude)_
- [x] **Q14 (AC-3, AC-4, AC-8, non-blocking):** Missing edge cases in create validation: explicit `null` for a required field, wrong JSON types (for example `category: 123`), unknown or extra fields (reject or ignore), empty body, malformed JSON, and non-object bodies. Should each return 422 (malformed JSON returns 422 or 400 in FastAPI)? Suggest adding one AC listing these.
  **Answer:** All of these return 422 in the Q10 error shape: null for a required field, wrong types, unknown or extra fields (rejected, not ignored), empty body, malformed JSON, non-object body. Add one AC that lists them. _(demo answer by Claude)_
- [x] **Q15 (AC-13, AC-16, non-blocking):** Edge cases for list filter parameters are unspecified: empty values (`category=`, `from=`), repeated parameters (`category=a&category=b`), and whitespace-only category. Options: treat an empty value as "not supplied", or return 422. `from == to` (single day) should be stated as valid, since AC-16 only says `from` later than `to` is invalid.
  **Answer:** An empty value counts as not supplied. A repeated `category` returns 422. `from == to` is valid and means a single day. _(demo answer by Claude)_
- [x] **Q16 (AC-9, AC-18, non-blocking):** Is there a maximum number of stored expenses, a maximum amount, or an overflow or limit on the total? With no pagination, the list response is unbounded (the NFR tests 10,000 items). State the expected behaviour or explicitly accept it. Related to Q5.
  **Answer:** Accept an unbounded list for this release (no maximum count or amount, matching Q5). Pagination is a follow-up item. _(demo answer by Claude)_
- [x] **Q17 (AC-19, non-blocking):** Duplicates are allowed with no idempotency key, so a client retry after a timeout silently double-counts spending. Confirm this is acceptable for this release, or add an optional `Idempotency-Key` header as a follow-up item.
  **Answer:** Duplicates are acceptable for this release. `Idempotency-Key` is a follow-up item. _(demo answer by Claude)_
- [x] **Q18 (Concurrency and storage, non-blocking):** Concurrent creates are not covered. With in-memory storage under FastAPI's threadpool, ID generation and list appends need to be thread-safe. Multiple server workers (`uvicorn --workers N`) would each hold a separate in-memory store and give inconsistent lists. Should the spec require a single worker, or does this push the decision on Q4 towards SQLite? Add an AC or NFR, for example "50 parallel creates yield 50 distinct IDs and a list of 50".
  **Answer:** Covered by SQLite (Q4). Run a single worker for now. Add an NFR: 50 parallel creates yield 50 distinct IDs and a list of 50. _(demo answer by Claude)_
- [x] **Q19 (NFR performance, non-blocking):** "200 ms on a developer machine" is not reproducible. Define the benchmark: the measured percentile (for example p95), whether it uses the in-process test client or a real server, and whether it is an automated test or a manual check. Otherwise it is untestable and flaky in CI.
  **Answer:** Automated test using the in-process TestClient: seed 10,000 expenses, make 20 list calls, p95 under 200 ms. Mark it `perf` so it runs on demand and not in every CI run. _(demo answer by Claude)_
- [x] **Q20 (AC-1 to AC-19, non-blocking):** Test isolation: the tests rely on "Given an empty store" and on fixed stored sets. The spec should require a way to reset the store between tests (a fixture, or dependency injection of the store). It affects Design, because a module-level global store in `app/main.py` would leak state between tests.
  **Answer:** Yes. Inject the store through a FastAPI dependency. Each test uses its own temporary SQLite file. _(demo answer by Claude)_
- [x] **Q21 (AC-20, non-blocking):** Existing code check: `app/main.py` currently defines only `app = FastAPI(title="Expense API")` and `GET /health` (lines 3 to 8). There is no conflict, but the impact section should state that the new routes must not change `/health` or the app title, and whether a `/expenses` router is mounted from `main.py` (line 3 onwards). AC-20 only covers the `/health` response body, not its status code (200) or the OpenAPI title.
  **Answer:** Confirmed. `/health` (status 200 and body) and the app title stay unchanged. Expenses live in an `app/expenses/` router mounted from `main.py`. AC-20 also covers the 200 status. _(demo answer by Claude)_
